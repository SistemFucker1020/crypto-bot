# Как бот остаётся живым

На Render Free процесс засыпает после **15 минут без входящего HTTP-трафика**.
Бот сам ходит в Telegram наружу (long polling), входящего трафика у него нет
поэтому вообще — без внешнего пинга он встаёт вместе с фоновой автопроверкой
рынка и перестаёт отвечать на команды.

Держат его живым **три независимых канала**.

## 1. Локальный пингер (основной)

`keepalive.sh` под systemd, ходит на `/health` **каждые 4 минуты**,
лог — `/home/admin/keepalive/keepalive.log`.

Почему основной, а не GitHub: замер за 19 часов (06.10 11:31 → 07.10 06:37 UTC)
показал, что расписание GitHub отработало **всего 4 раза** вместо ~230:

```
15:50:29 → 20:41:22 → 00:10:44 → 06:04:36     промежутки 4ч51м, 3ч30м, 5ч54м
```

Каждый такой прогон будит сервис на 15 минут, дальше он снова засыпает.
То есть ночью бот жил примерно час из девятнадцати.

### Восстановление с нуля

```bash
mkdir -p /home/admin/keepalive ~/.config/systemd/user
cp ops/keepalive.sh   /home/admin/keepalive/keepalive.sh
cp ops/keepalive.service ~/.config/systemd/user/keepalive.service
chmod +x /home/admin/keepalive/keepalive.sh
systemctl --user daemon-reload
systemctl --user enable --now keepalive.service
sudo loginctl enable-linger admin     # автозапуск после загрузки машины
```

### Проверка

```bash
systemctl --user status keepalive.service
tail -5 /home/admin/keepalive/keepalive.log
curl -s https://crypto-bot-im58.onrender.com/health
```

В логе каждые 4 минуты строка вида
`2026-10-07T06:44:14Z HTTP 200 {"status": "ok", ...}`.
`HTTP 000` — сеть или DNS не ответили; это нормально на первых минутах
после загрузки машины, дальше ошибка сама лечится: цикл не прерывается.

## 2. GitHub Actions (второй канал и оповещение)

`.github/workflows/keep-alive.yml` — `GET /health` каждые 5 минут.
Если сервис не отвечает или `/health` отдаёт 503 (автопроверка не бегла
45 минут), job падает и **GitHub присылает письмо**. Это единственный
автоматический способ узнать о проблеме, пока ты не открывал бота.

Особенности:

- `404` трактуется как «на сервере старая версия без `/health`» — даёт
  warning в логе, но job не валит, иначе сыпались бы письма каждые 5 минут;
- триггер `push` с фильтром `paths` на сам workflow — нужен, чтобы
  проверить, запускаются ли Actions вообще;
- `workflow_dispatch` — ручной запуск из вкладки Actions.

## 3. UptimeRobot (внешний, держит один)

[UptimeRobot](https://uptimerobot.com) — бесплатный монитор на **5 минут**
(порог сна Render — 15), карта не нужна, хватает 50 мониторов. Монитор
`crypto-bot` → `https://crypto-bot-im58.onrender.com/health`, интервал 300 с.
Единственный канал, который **не зависит от твоей машины**: локальный пингер
умер вместе с ноутбуком, GitHub отрабатывает раз в 2–4 часа, а UptimeRobot
будит сервис и в твоё отсутствие.

Проверено опытом 09.10: локальный пингер остановили на 18 минут, GitHub
за окно не запускался (0 запусков), а сервис не заснул ни на секунду —
`uptime` вырос непрерывно `3983 → 5063 c`. Значит, монитор реально бьёт.

Оповещения: `Monitoring → crypto-bot → Edit → «Alert Contacts To Notify»`
→ галочка на своём e-mail → **Save Changes** (без сохранения галочка не
применяется). Контакт создаётся в профиле → «My Settings → Alert Contacts».

API-ключ монитора (read-only) — для диагностики:

```bash
curl -s -X POST https://api.uptimerobot.com/v2/getMonitors \
  --data-urlencode "api_key=<мониторный-ключ>" --data "format=json&logs=1"
# status: 2 — UP; проверка ответа сервиса: response_time
```

## Подписка чата на сигналы

Сигналы уходят только чатам с включённой подпиской:

```
/signals on    — подключить этот чат (работает и в группе)
/signals off   — отключить, чат остаётся в базе
/signals       — статус: подключён ли чат, сколько чатов получает сигналы,
                 расписание, порог подтверждения, состояние переменной
```

`/start` тоже подписывает чат — старый сценарий «просто напиши боту» работает.

Чтобы подписка **переживала деплой**, в настройках Render задаётся переменная
`TELEGRAM_CHAT_IDS` — список чатов через запятую (`123456,-100789`). Готовую
строку бот печатает сам в ответе на `/signals on`, `/signals` и `/start`.
Старое имя `TELEGRAM_CHAT_ID` тоже читается. Если переменная не задана, бот
пишет об этом в лог при старте и в статусе подписки.

Переменную заполняют руками, поэтому при старте **каждый ID из неё
проверяется в Telegram** (`get_chat`): несуществующий чат не подписывается,
попадает в лог предупреждением и в статус `/signals` меткой `❌ не найден`,
такой ID подсказка перестаёт советовать. Если Telegram в этот момент
недоступен — чат подписывается всё равно, статус остаётся `… не проверен`,
чтобы обрыв связи не лишал пользователя сигналов. Проверка занимает не
больше 25 секунд, чтобы старт процесса не завис.

## Paper trading — настоящие ордера (Bybit или OKX Demo)

Сигнал не остаётся в переписке: по подтверждённому сигналу бот ставит
**реальный ордер на бирже** — вход маркет, стоп-лосс и тейк-профит живут
на бирже и срабатывают сами. Деньги фальшивые, всё остальное настоящее.

Биржу выбирает окружение, код один:

- заданы `OKX_*` → бот торгует на **OKX Demo** (фьючерсы, плечо, стопы);
- без них → **Bybit**, как раньше (по умолчанию тестнет).

По умолчанию — тестнет Bybit, поэтому бумагой это остаётся, пока не
поменяешь переменную.

Переменные (все в настройках Render, в git не попадают):

| Переменная | Нужна | Что делает |
|---|---|---|
| `BYBIT_KEY` / `BYBIT_SECRET` | да | ключи тестнета: testnet.bybit.com → Profile → API |
| `BYBIT_TESTNET` | нет | `1` (по умолчанию) — тестнет, `0` — боевой счёт |
| `PAPER_TRADING` | нет | `1` (по умолчанию) — ордера включены при наличии ключей |

Команды в чате:

```
/paper        — статус: режим, ключи, баланс, открытая позиция
/paper on     — включить выставление ордеров (запоминается в базе)
/paper off    — только сигналы, без ордеров
/positions    — открытые позиции, последние закрытые сделки, журнал ордеров
/stats        — плюс реализованный PnL и доля прибыльных сделок с биржи
```

Под сигналом появляется кнопка **«🛑 Закрыть позицию»** — снимает
ожидающие ордера и закрывает позицию по рынку, показывая PnL.

Как считается вход:

- размер позиции берётся из расчёта риска (`size = position / entry`),
  режется вниз до шага лота биржи и проверяется на минимальный объём;
- цена сверяется с `entry` сигнала: ушла дальше `MAX_ENTRY_DRIFT` — ордер
  не ставится, причина уходит в чат вместе с сигналом;
- пока открыта позиция, второй ордер не ставится;
- стоп округляется **в сторону, удалённую от входа** — округление к входу
  сузило бы риск, а риск считает код;
- любая ошибка биржи попадает в то же сообщение, что и сигнал, и не
  отменяет его: упавший тестнет не должен прятать торговый сетап.

Позиция читается с биржи, а не из базы, поэтому переживает рестарт
процесса и стирание файловой системы на Render. Журнал ордеров дублируется
в `positions` для истории.

Переход на реальные деньги: `BYBIT_TESTNET=0` + боевые ключи (или
`OKX_DEMO=0` на OKX). Код не меняется — это и есть цель: сначала 2–3 недели
paper trading, потом те же самые ордера на боевом счёте.

## OKX Demo — почему и как подключить

У тестнета Bybit есть ограничение, которое не обойти: **там только спот**.
Фьючерсы с плечом есть только на боевом ключе, а чужие деньги в работу
брать нельзя. OKX Demo снимает это честно: живые котировки, перпетуал
`BTC-USDT-SWAP`, плечо, стоп и тейк — всё настоящее, деньги бумажные,
ключ не имеет доступа к боевому счёту.

| Переменная | Нужна | Что делает |
|---|---|---|
| `OKX_KEY` / `OKX_SECRET` / `OKX_PASSPHRASE` | да | ключ Demo Trading API (все три вместе) |
| `OKX_DEMO` | нет | `1` (по умолчанию) — заголовок `x-simulated-trading: 1`, `0` — боевой счёт |
| `OKX_INST_ID` | нет | `BTC-USDT-SWAP` (по умолчанию) |
| `OKX_API` | нет | `https://www.okx.com` (по умолчанию) |

Создание ключа: на okx.com включи режим **Demo Trading** (Trade → Demo
Trading) → аватар → **Demo Trading API** → Create → задай passphrase →
права **Read + Trade**. Ключ, секрет и passphrase уходят в настройки
Render, в git не попадают.

Проверка ключа до настройки Render — из корня репозитория:

```bash
OKX_KEY=... OKX_SECRET=... OKX_PASSPHRASE=... \
  .venv/bin/python /tmp/opencode/okx_check.py
```

Тонкости адаптера `okx.py`:

- шаг лота OKX задан в **контрактах** (`lotSz × ctVal`), бот считает
  монетами — поэтому в чат и журнал попадают монеты, контракты считаются
  только при отправке ордера;
- стоп и тейк уходят приложенным алго-ордером (`attachAlgoOrds`), снимаются
  `cancel_all` вместе с ожидающими ордерами;
- направление учитывает режим позиции аккаунта (односторонний/хедж) —
  режим один раз читается из `account/config`;
- `positions-history` даёт `realizedPnl` уже с комиссией, как `closedPnl`
  у Bybit, — суммы с двух бирж сравнимы;
- сигнал считается по данным Bybit (публичный API), поэтому вход защищён
  проверкой дрейфа `MAX_ENTRY_DRIFT`: расхождение двух бирж меньше лимита.

## Сигнальный конвейер — уровни, TTL, повторная проверка, Score, режим

Сигнал проходит цепочку проверок, каждая из которых может его отменить
(с причиной в журнал `/history`), но ни одна не может отправить его мимо
подтверждения `CONFIRM_REQUIRED`:

```
данные (≥3 источника) → конфлюэнция (встречный голос = стоп)
  → режим рынка (только явное правило REGIME_BLOCKS)
  → Score-гейт (порог SCORE_MIN + покрытие данных)
  → LLM подбирает вход (SL/TP НЕ задаёт)
  → уровни кодом (levels.py): стоп за уровнем отмены, TP — первый
    реальный уровень с R:R ≥ MIN_RR, нет такого — WAIT
  → Risk Engine (чистый бюджет, потолок NET_RISK_MAX_PCT)
  → TTL: сигнал действует SIGNAL_TTL_* от формирования
  → подтверждение CONFIRM_REQUIRED за CONFIRM_WINDOW_SEC
  → повторная проверка (RECHECK_DELAY_SEC): направление, дрейф цены,
    уровни, Score, режим, свежесть данных — иначе отмена
  → paper-вход (TTL и дрейф ещё раз) → отправка в чат
```

Ключевые свойства:

- **TP не растягивается ради R:R.** Цель — только реальный уровень с графика
  (свайпы, стенки, граница диапазона). Ближайшая цель даёт R:R меньше
  `MIN_RR` — сигнал уходит в WAIT, а не получает выдуманный тейк.
- **Чистый убыток по стопу ≤ `NET_RISK_MAX_PCT` (5%) баланса** даже при
  тесном стопе и 10x: позиция считается от чистого бюджета
  `position = budget / (стоп + издержки)`, поэтому комиссии, funding и
  проскальзывание не выводят убыток за бюджет. Ограничение честное:
  при ценовом гэпе стоп может исполниться хуже заявленного.
- **TTL:** по умолчанию две свечи таймфрейма (`SIGNAL_TTL_15M=1800`,
  `SIGNAL_TTL_1H=7200`). Истёкший сигнал не отправляется и не ставит
  ордер, в `/history` виден как `expired`.
- **Повторная проверка:** после подтверждения бот ждёт `RECHECK_DELAY_SEC`
  (0 — выключить) и собирает рынок заново. Отменяет при: смене направления,
  дрейфе цены дальше `MAX_ENTRY_DRIFT`, потере источников, устаревших
  данных (старше `RECHECK_MAX_AGE_SEC`), падении Score, заблокированном
  режиме. Причина уходит в журнал (`cancelled`).
- **Score 0–100 — НЕ вероятность прибыли**, а сила согласованности семи
  групп факторов (структура, order flow, OI/funding, ликвидации, объём,
  тренд 1h, стакан). Группа без реальных данных не начисляет баллов и
  снижает покрытие; при покрытии ниже `SCORE_MIN_COVERAGE` сигнал
  отклоняется. Веса — `SCORE_W_*`, калибровки на истории пока нет,
  поэтому утверждать «Score 80 = 80% успеха» нельзя.
- **Режим рынка** (TREND/RANGE/HIGH_VOLATILITY/LOW_VOLATILITY/NEWS_EVENT/
  UNKNOWN) детерминирован считает Python и сохраняется в журнал. Сам по
  себе не блокирует: фильтрация только через явное `REGIME_BLOCKS`.
- **Журнал:** каждая запись хранит время формирования/истечения/отправки,
  Score с разбивкой групп, режим с флагами, снимок рынка и оценку
  издержек — любое решение разбирается постфактум. Миграция базы только
  добавляет колонки, история не удаляется.

### Переменные сигнального конвейера

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `SIGNAL_TTL_15M` / `SIGNAL_TTL_1H` | `1800` / `7200` | срок действия сигнала, сек (по таймфрейму) |
| `RECHECK_DELAY_SEC` | `10` | пауза перед повторной проверкой; `0` — выключить |
| `RECHECK_MAX_AGE_SEC` | `120` | данные старше — повторная проверка отменяет сигнал |
| `SCORE_MIN` | `60` | минимальный Score для отправки (0–100) |
| `SCORE_MIN_COVERAGE` | `0.6` | минимальное покрытие данных групп Score |
| `SCORE_W_STRUCTURE` / `_ORDERFLOW` / `_OI` / `_LIQ` / `_VOLUME` / `_HTF` / `_BOOK` | `20/15/15/10/10/15/15` | веса групп Score (сумма 100) |
| `REGIME_BLOCKS` | пусто | режимы, блокирующие сигнал, напр. `HIGH_VOLATILITY,NEWS_EVENT` |
| `REGIME_ADX_TREND` / `REGIME_ADX_RANGE` | `25` / `18` | пороги ADX: тренд / боковик |
| `REGIME_ATR_HIGH_VOL` / `REGIME_ATR_LOW_VOL` | `0.5` / `0.1` | пороги ATR% всплеска/затишья |
| `NET_RISK_MAX_PCT` | `5` | жёсткий потолок чистого убытка по стопу, % баланса |
| `FEE_TAKER_PCT` / `SLIPPAGE_PCT` | `0.05` / `0.02` | оценка комиссии и проскальзывания за сторону, % |
| `FUNDING_PCT` / `FUNDING_INTERVAL_H` / `PLAN_HOLD_H` | `0.01` / `8` / `8` | оценка funding и планового удержания |
| `SL_ATR_BUFFER` / `SL_MIN_BUFFER_PCT` / `INVALIDATION_ATR` | `0.5` / `0.15` / `1.5` | буфер стопа за уровнем (ATR / мин.% цены / ATR-инвалидация) |

Все оценки издержек — **оценки**: фактическую комиссию биржа отдаёт
в закрытых сделках, `/stats` показывает валовый и чистый PnL оттуда
отдельно от плановых сумм.

### Проверка paper trading после изменений

1. Деплой на Render, `curl -s .../health` → `{"status": "ok"}`.
2. `/history` — старые записи на месте (миграция не стёрла историю).
3. `/predict` — сигнал или WAIT с понятной причиной; в сигнале видны
   `Score`, `Режим рынка`, `Уровни` и `Сигнал действителен до …`.
4. Дождаться автосигнала или `/predict` вручную: в `/history` запись
   со статусом `sent` (или `manual`), с `sent_at`, Score и режимом.
5. `/stats` — сформировано/отправлено/отменено/истекло расходятся,
   плановые суммы подписаны как оценка, реализованные — с биржи.
6. Лог Render: строки `повторная проверка пройдена` или
   `отменён повторной проверкой: <причина>`.

Тесты (без сети, временная база):

```bash
.venv/bin/python tests/test_health.py        # живость бота и paper trading
.venv/bin/python tests/test_signal_quality.py # уровни, TTL, recheck, Score, режим
```

## Что чинит сам бот

- `run_polling()` — сбой сети Telegram больше не убивает процесс;
- `scheduler()` — цикл автопроверок не может умереть молча;
- `/health` — 503, если рынок никто не смотрит, хотя HTTP в целом жив;
- `TELEGRAM_CHAT_IDS` — подписки переживают рестарт (Render стирает
  `signals.db` при каждом засыпании и деплое), а несуществующие чаты
  из переменной отсеиваются при старте.

Проверяется всё одной командой из корня репозитория:

```bash
.venv/bin/python tests/test_health.py
```
